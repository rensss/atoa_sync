# 架构决策记录

决策记录采用追加式维护。若要改变已接受决策，必须先获得用户批准，再新增一个明确
supersede 旧决策的 ADR。

## ADR-001：平台拥有的仓库布局

- 日期：2026-06-08
- 状态：已接受

背景：活跃 Android 和 macOS 文件曾混在仓库根目录。

决策：Android 实现归属 `android/`；macOS 实现归属 `macos/`；共享元数据和发布
内容保留在根目录。

后果：每个平台可以独立理解和构建。平台专属文件不得漂回根目录。

## ADR-002：原生 macOS 接收端是受支持接收端

- 日期：2026-06-08
- 状态：已接受

背景：独立 Python 接收端重复了原生 macOS 功能。

决策：移除 Python 接收端，使用
`macos/Sources/AndroidSyncCore/ReceiverService.swift` 作为受支持的本地电脑端接收器。

后果：接收协议和存储变更必须在 `AndroidSyncCore` 中实现并测试。

## ADR-003：保留现有平台工具链

- 日期：2026-06-08
- 状态：已接受

背景：Android 应用使用直接 Android SDK 脚本，macOS 应用使用 SwiftPM、SwiftUI 和
SwiftData。

决策：稳定性和 UX 重构期间继续使用这些工具链。

后果：引入 Gradle、第三方 Android 库、其他 macOS 包管理器或替换 UI 框架，都需要
supersede ADR。

## ADR-004：先流式暂存再原子提交上传

- 日期：2026-06-08
- 状态：已接受

背景：部分网络传输不能以完整媒体形式出现在媒体库中。

决策：上传先流式写入 `.incoming/*.part`，校验期望尺寸后，再把完成文件移动到最终
日期媒体目录。

后果：每个错误和取消路径都必须清理临时文件。禁止直接写入最终媒体路径。

## ADR-005：追加式 manifest 和 tombstone

- 日期：2026-06-08
- 状态：已接受

背景：Android reconciliation 需要持久知道已存储和已删除的媒体。

决策：在 `uploads.jsonl` 中记录 stored 和 deleted 事件；删除使用 tombstone 表示，
而不是擦除历史。

后果：读取方必须按稳定 ID 推导最新状态，并容忍历史记录。未来 compaction 必须
保持等价语义。

## ADR-006：当前发布面向可信局域网

- 日期：2026-06-11
- 状态：已接受风险

背景：当前协议使用明文 HTTP 且没有认证。

决策：当前操作限制在可信私有/链路本地网络。

后果：文档不得暗示可安全部署到互联网。公网暴露、认证或 TLS 需要单独安全决策和
协议设计。

## ADR-007：批次治理式演进

- 日期：2026-06-11
- 状态：已接受

背景：稳定性、并发、存储和 UI 工作有不同失败模式和验证需求。

决策：非平凡工作以小批次实现，并在 `PROJECT_MEMORY/batches/` 记录范围、风险、
验证证据和回滚说明。

后果：大型一次性重构不符合已批准执行模型。里程碑完成需要累积批次证据。

## ADR-008：Android 后台同步由前台服务和本地任务数据库拥有

- 日期：2026-09-20
- 状态：已接受

背景：上传线程原先属于 `MainActivity`，Activity 销毁或进程终止会丢失内存队列和
活动任务，无法可靠支持退后台、锁屏和恢复。

决策：用户主动确认同步后，由 `SyncForegroundService` 独占上传生命周期；
`SQLiteOpenHelper` 持久化任务、run、目标 URL 快照和选择顺序；Activity 只负责扫描、
确认、展示和发送 Service 命令。保留单线程整文件 HTTP PUT、每文件一次尝试和现有
macOS 接收协议，不增加 WorkManager、开机自启、自动重试或字节级续传。

后果：系统允许时 `START_STICKY` 可以恢复 `RUNNING` run，Service 启动前把遗留
`UPLOADING` 恢复为 `WAITING` 并查询远端 manifest；厂商电池策略和用户强制停止仍
可能中断服务，manifest 不可用时仍接受重复整文件上传的限制。

## ADR-009：macOS 接收目录按类型平铺并保留源文件时间戳

- 日期：2026-09-21
- 状态：已接受；supersedes ADR-004 的按月最终目录决策

背景：按接收月份分目录会把同一类型的媒体拆散；上传完成后直接移动文件还会使文件
系统创建时间看起来像传输时间，不能保留源文件时间信息。

决策：macOS 新上传直接写入所选根目录下的 `photos/`、`videos/` 或 `files/`，不再创建
`YYYY-MM` 子目录。文件系统创建时间和修改时间统一按源时间设置，优先级为
`dateModified` → `dateTaken` → `dateAdded` → 实际接收时间。已有按月目录不自动迁移，
由 `uploads.jsonl` 中的历史路径继续提供兼容读取。

后果：新旧布局在同一接收根目录中可以并存；文件命名冲突仍通过唯一后缀解决，旧目录
迁移另行设计，不能在接收时隐式移动用户文件。
